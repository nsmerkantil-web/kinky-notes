# Локальные модели для A-notes: качество, скорость и нагрузка

Дата: 6 ноября 2026, Asia/Tbilisi.

Статус: исследование официальных карточек, документации, исходников A-notes и метаданных установленных моделей. Новые веса не скачивались, сравнительный inference-бенчмарк не выполнялся, рабочие встречи не читались. Рекомендации ниже — приоритеты проверки, а не измеренный рейтинг качества или скорости. Код и настройки приложения не менялись.

## Вывод для выбора

Первым сравнить **Qwen3.5-4B Q4_K_M** как основной вариант и **Liquid LFM3-1.7B Q4_K_M** как экономичный вариант. В качестве контроля оставить установленную `gemma4:latest`; дополнительно проверить Gemma 4 E2B. Поддерживаемые в первой версии подключения Ollama/LM Studio позволяют проверять эти модели без нового пользовательского типа подключения, но совместимость конкретного checkpoint с установленным runtime нужно подтвердить.

Для хранения и редактирования заметок генеративная модель не нужна. Для поиска по смыслу нужна отдельная небольшая embedding-модель. Для извлечения типизированных полей и классификации интересны decision-модели. Для подробного связного итога остаётся полезна компактная генеративная модель. Практический выигрыш даст разделение задач и управление памятью, а не обязательная замена всего на одну необычную архитектуру.

## 1. Требования именно нашего продукта

Подтверждено текущим кодом `Conversation.analysisPrompt`, `SummaryService`, `SpeakerAttributionService`, хранилищем и ранее согласованным поведением:

| Задача | Что требуется | Подход |
| --- | --- | --- |
| Аудио → полный RU/EN-транскрипт | Имена, смешанная речь, временные метки | ASR; это отдельный выбор от текстовой модели |
| Подробные заметки встречи | Конкретные темы, позиции, примеры, аргументы и факты; не общий абзац | Компактная instruction-модель |
| Решения и действия | Только явные договорённости; точные ответственные/сроки; не превращать предложения в решения | Генерация с проверкой источника; позднее extraction/decision-модель |
| Личные разговоры | Сохранять переживания и неопределённость, не добавлять диагнозы и деловые шаблоны | Проверка качества на отдельной части корпуса |
| Название | Короткое название по содержанию; не переписывать ручное | Та же уже загруженная модель |
| Папки, файлы, сохранение, экспорт | Детерминированность и сохранность | Обычный код и локальные файлы |
| Теги | Небольшой закрытый набор или свободные темы | Правила/классификатор; генерация только при необходимости |
| Поиск по словам | Точный поиск имён, проектов, формулировок | Индекс текста, без LLM |
| Поиск по смыслу | Похожие темы и релевантные фрагменты | Небольшие multilingual embeddings |
| Вопросы по архиву, если добавим | Ответ по найденным фрагментам с происхождением | Retrieval + компактная LLM; не весь архив в prompt |

Архивные QA, embeddings и decision API здесь — варианты развития, не заявление о реализованных функциях A-notes.

## 2. Что установлено и проверено сейчас

Локальная машина: **Apple M4 Pro, 48 GiB unified memory, macOS 26.6.2**. Ollama API сообщает версию **0.40.13**.

| Установленный тег | Размер из локального `/api/tags`, десятичные GB | Примечание |
| --- | ---: | --- |
| `gemma4:latest` | 9.61 | `/api/show`: 7 996 157 674 параметра, архитектура gemma4, Q4_K_M |
| `gemma3:27b` | 17.40 | Большой пресет для массовой версии продукта |
| `qwen3-vl:30b` | 19.60 | Мультимодальность для текстовых заметок не обязательна |
| `gpt-oss:20b` | 13.79 | Большой пакет; не исходный экономичный вариант |

Размеры — файлы/пакеты, не измеренный пик RAM. Тег `latest` не является достаточно точной спецификацией публичного checkpoint; в сравнении нужно сохранять digest, quantization, backend и chat template. Нельзя переносить прошлые результаты «Gemma» на другую версию с похожим названием.

Этот Mac позволяет проверить тяжёлые варианты, но их пригодность для массового продукта следует отдельно оценивать на Mac с 8/16 GiB. Количество активных параметров MoE или обозначение E2B/E4B не равно объёму всех весов.

## 3. Кандидаты для генерации

### Qwen3.5-4B: основной кандидат на баланс

Официальный checkpoint post-trained, Apache 2.0. В 4B-варианте чередуются Gated DeltaNet и attention: это гибридная модель, хотя она всё ещё генерирует авторегрессионно. Поддержку multilingual и отключение thinking описывает разработчик. [Карточка Qwen](https://huggingface.co/Qwen/Qwen3.5-4B).

Причина включения: умеренный размер и подходящий профиль задач. Это гипотеза, которую нужно проверить на точности RU/EN-конспектов. Полезная инструкция-модель не обязана быть 20B/27B. Она должна пройти проверки имён, отрицаний, изменённых решений и поздних договорённостей.

На странице Ollama сейчас показаны разные артефакты: **3.3 GB для llama.cpp/Q4_K_M** и **4.0 GB для MLX**. Указывать «4B Q4 = ровно 2 GB» для готового пакета неверно: есть другие тензоры и мультимодальные ресурсы. [Ollama tag](https://ollama.com/library/qwen3.5:4b).

Стартовый тест: GGUF Q4_K_M и MLX 4-bit с одинаковым содержимым prompt и без reasoning traces. Не объявлять один backend быстрее без измерения полного задания.

### Liquid LFM3-1.7B: приоритетный экономичный эксперимент

Свежий text-only checkpoint, заявлена поддержка русского. Архитектура сочетает короткие свёртки, sliding-window и global attention. В отличие от LFM2.5-1.2B, русский уже входит в список языков. Ограничение: маленькая модель не доказывает полноту сложного конспекта, а reasoning включён по умолчанию; разработчик предупреждает, что отключение может работать непоследовательно. [Карточка LFM3](https://huggingface.co/LiquidAI/LFM3-1.7B), [релиз разработчика от 27 октября](https://huggingface.co/blog/LiquidAI/lfm3).

По проверенному HF API метаданных официальный `LFM3-1.7B-Q4_K_M.gguf` занимает **1 099 627 808 байт**, Q5_K_M — **1 258 663 200 байт**. Revision: `cd0c74c575b5c416f3011b5b4c298077f26ca8c2`. Это размер файла, не обещание, что весь процесс с длинным контекстом уложится в 1 GB RAM. [Официальные GGUF](https://huggingface.co/LiquidAI/LFM3-1.7B-GGUF).

Начать с Q4, при ошибках имён/сроков сравнить Q5. Оценивать отдельно обычные рабочие встречи и личные беседы. Лицензия — LFM Open License, не автоматически Apache/MIT; условия распространения конкретных весов проверяются до включения в app.

### Gemma 4 E2B: контрольный малый вариант

Полезен для сравнения с нынешней семьёй Gemma. Но «effective 2B» не описывает все embedding-таблицы и мультимодальные компоненты. Официальная карточка прямо различает effective и total parameters. [Gemma 4](https://ai.google.dev/gemma/docs/core/model_card_4).

Текущая страница Ollama показывает **4.6 GB для GGUF-пакета** и **7.5 GB для MLX-варианта**. Не считать E2B автоматически самым лёгким скачиванием среди 2B/4B-кандидатов. [Ollama E2B](https://ollama.com/library/gemma4:e2b).

### Qwen3.5-2B: дополнительная точка на кривой качества

Если 4B окажется тяжеловат, проверить 2B, сохранив те же требования к фактам. Обязательно закреплять формат: текущий тег Ollama показывает **Q8_0**, а не Q4, и размер около 2.7 GB для llama.cpp-пакета. Сравнение с 4B Q4 иначе смешивает архитектуру и разрядность. [Checkpoint](https://huggingface.co/Qwen/Qwen3.5-2B), [tag и quantization](https://ollama.com/library/qwen3.5:2b).

### NVIDIA Nemotron 3.5 Bolt E4B 4GB: резервный вариант

Это дообученная Gemma 4 E4B, ориентированная на локальных ассистентов, instruction following и grounding. Есть GGUF и companion DFlash, но качество подробной RU-суммаризации на нашем корпусе неизвестно. [Карточка NVIDIA](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Bolt-E4B-4GB).

Название `4GB` не принимаем за замер: проверенный API репозитория для revision `1db54d5b12533ff1bcaa8e42cf4c667988a1f1be` сообщает **6 180 446 208 байт** для `Nemotron-3.5-Bolt-E4B-Q4_K_M.gguf`. Дополнительный draft — ещё отдельные ресурсы. В первый минимальный раунд можно не включать.

## 4. Специализированные и другие архитектуры

| Подход | Польза для A-notes | Почему не заменяет всё приложение |
| --- | --- | --- |
| Decision-модель, например d1-2B | Теги из заданного набора, классификация, извлечение явно названных людей/дат и source spans | Не генерирует связный конспект |
| Encoder-decoder, T5/ruT5/T5Gemma | Потенциальный небольшой специализированный суммаризатор после адаптации | Готовая модель может быть обучена на коротких новостях, а не встречах |
| TextRank/LexRank и правила | Быстрые ключевые слова/цитаты, резервное extractive-представление | Отдельные предложения теряют связь, коррекции и местоимения |
| RWKV/SSM/гибриды | Меньший рост состояния при длинном контексте у подходящей архитектуры | Архитектура не доказывает качество RU-конспекта или поддержку runtime |
| Text diffusion | Параллельная генерация блоков, потенциально низкая latency | Высокая скорость не гарантирует низкие RAM/энергию |
| Speculative decoding/MTP | Ускорение той же генеративной модели | Дополнительный runtime/draft, требования совместимости и свои затраты |

### Decision-модели: действительно применимая часть «сверхбыстрых» моделей

`LiquidAI/d1-2B` отвечает типизированными значениями и извлекает фрагменты за один forward pass, без последовательного генерирования токенов. Поддерживается русский. Это подходит для вопросов «есть ли явная договорённость?», «какой срок назван?» и классификации, но не для написания подробного итога. Ошибки возможны: нужны проверка spans и настройка порогов на нашем корпусе. [Первичная карточка d1](https://huggingface.co/LiquidAI/d1-2B).

Заявленные миллисекунды на H100/MI325X нельзя переносить на M4 Pro. Длинный вход также надо прочитать; один forward pass не делает длинную встречу бесплатной.

В LM Studio документированы `/v1/decisions` и `/v1/systemone`. Нынешний клиент A-notes вызывает chat completions и их не поддерживает. Потребуется отдельный адаптер и проверка поддержки именно выбранного decision-checkpoint в runtime. Автоматически сгенерированные «Use this model» snippets на HF не заменяют реальную инструкцию модели. [Decisions](https://lmstudio.ai/docs/developer/openai-compat/decisions), [System One](https://lmstudio.ai/docs/developer/jev-compat).

### Специализированный суммаризатор

`IlyaGusev/rut5_base_sum_gazeta` — показательный компактный готовый RU-суммаризатор, но его карточка описывает Gazeta и вход 600/выход 200 токенов в оценке. Это другой домен и формат. Для часового разговора потребуется разбиение, а затем проверка потери деталей. [ruT5 Gazeta](https://huggingface.co/IlyaGusev/rut5_base_sum_gazeta).

`T5Gemma 2` предлагает encoder-decoder размеры 270M–270M, 1B–1B и 4B–4B, multilingual и длинный контекст. Но конкретный открытый `1b-1b` — **pretrained**, а не готовый meeting assistant. Это кандидат под дообучение, не моментальная замена нынешнему клиенту. [Карточка Google](https://huggingface.co/google/t5gemma-2-1b-1b).

Дообучать небольшой суммаризатор разумно после появления согласованного качественного корпуса «транскрипт → наши подробные заметки» и независимого теста. Сам факт специализации не гарантирует скорость: длина выхода, beam search и runtime также влияют.

### RWKV и другие модели со сжатым состоянием

RWKV-7 — рекуррентная архитектура с постоянным относительно длины контекста состоянием вместо обычного растущего KV cache. Это привлекательное свойство, но не гарантия точного восстановления редкого имени, отрицания или поздней поправки. Выбор проверяется по конкретным весам и Metal/runtime, а не только асимптотике. [Репозиторий разработчика](https://github.com/BlinkDL/RWKV-LM).

Официальная работа TextRank описывает извлечение ключевых слов/предложений без нейросетевого генератора. В A-notes это полезно как «ключевые фрагменты», но нельзя выдавать такой результат за содержательно связный итог. Не отбрасывать навсегда «малозначимые» реплики перед LLM: в них могут находиться изменённый срок или отмена решения. [TextRank](https://aclanthology.org/W04-3252/).

### Диффузионная генерация и ускоряющие drafts

DiffusionGemma генерирует блоки текста с параллельным уточнением. Однако текущий вариант основан на 26B/A4B, поэтому это не эквивалент маленькой 4B-модели по хранению всех весов. В первом раунде экономичных моделей не приоритет. [Описание](https://ai.google.dev/gemma/docs/diffusiongemma), [архитектура](https://ai.google.dev/gemma/docs/diffusiongemma/model_card).

Speculation/MTP — способ ускорить генерацию, а не отдельный тип суммаризации. MLX-LM поддерживает draft-модели, но есть требования к tokenizer/cache и конкретной архитектуре. Измерять надо полное время и пиковую память; для коротких названий затраты на draft могут не окупиться. [MLX-LM](https://github.com/ml-explore/mlx-lm).

Splash в LM Studio — интересный пример специализированного backend + DFlash для Qwen3.8-27B и Qwen3.6-35B-A3B. Но требования минимум 36 GB памяти и определённые новые Mac/OS делают его вариантом для нашего мощного Mac, а не общей экономичной рекомендацией. Опубликованные результаты M5 Pro не являются измерениями на нашем M4 Pro. [LM Studio Splash](https://lmstudio.ai/blog/splash-engine).

## 5. Альтернативы самим Ollama и LM Studio

Ollama/LM Studio — приложения и серверы, Llama/Qwen/Gemma/LFM — семейства моделей, llama.cpp/MLX — inference-технологии. Можно использовать Qwen через уже выбранную Ollama или MLX через LM Studio; это не взаимоисключающие решения.

- **llama.cpp непосредственно:** возможный встроенный движок/дочерний сервер без обязательной установки Ollama. Нужны собственные model lifecycle, обновления и совместимость. Название llama.cpp не означает поддержку только Llama. [Проект](https://github.com/ggml-org/llama.cpp).
- **MLX непосредственно:** родная для Apple Silicon технология. Для нативной app есть MLX Swift LM; поддержка нужной архитектуры должна подтверждаться конкретной версией. [MLX Swift LM](https://github.com/ml-explore/mlx-swift-lm).
- **LM Studio с MLX:** практический тест backend без нового провайдера A-notes. Преимущества в чужих агентных бенчмарках не равны ускорению наших конспектов. [Описание движка](https://lmstudio.ai/blog/mlx-engine-agentic-workloads).
- **Apple Foundation Models:** привлекательный системный путь без поставки отдельного LLM runtime, но имеет OS/device/locale ограничения. На этом Mac read-only запрос API вернул `appleIntelligenceNotEnabled`; в `supportedLanguages` текущей модели русского нет. Настройки Apple Intelligence не менялись. Это не означает, что русский отсутствует во всех новых поколениях AFM: Apple описывает расширение языков в AFM 3. [Проверка локали](https://developer.apple.com/documentation/foundationmodels/supporting-languages-and-locales-with-foundation-models), [AFM 3](https://machinelearning.apple.com/research/introducing-third-generation-of-apple-foundation-models).

Для документированного базового on-device API Apple описывает 4096 токенов на сессию; нельзя помещать туда часовой транскрипт целиком. Новые профили/версии требуют отдельной проверки. Если такой путь добавлять, выбирать явно on-device, не делать автоматического перехода на PCC при обещании офлайн-режима. [Context management](https://developer.apple.com/documentation/foundationmodels/managing-the-context-window).

Изменять согласованный scope v1 не требуется: сначала сравнить модели через имеющиеся подключения. Прямое встраивание движка — следующий отдельный продуктовый выбор.

## 6. Поиск и хранение

Хранение — обычные Markdown/JSON и индексы, а не «память» постоянно запущенной LLM. Для semantic search сначала проверить **multilingual-e5-small**: около 0.1B параметров, но вход ограничен 512 токенами, значит индексировать нужно фрагменты. [Карточка e5](https://huggingface.co/intfloat/multilingual-e5-small).

Другой вариант — текстовая EmbeddingGemma первого поколения, около 300M и 2K input. Более новая EmbeddingGemma 2 — отдельная модель с иной конфигурацией; не смешивать её размеры с первой. Для наших текстов не нужно автоматически загружать мультимодальный пакет. [Первая модель](https://ai.google.dev/gemma/docs/embeddinggemma/model_card), [второе поколение](https://ai.google.dev/gemma/docs/embeddinggemma).

Эмбеддинги сохраняются один раз для нового/изменённого фрагмента. Поиск по смыслу должен дополнять точный поиск имён и проектов. Генеративная модель загружается только если нужен сформулированный ответ, а не для показа списка найденных заметок.

## 7. Где снизить нагрузку независимо от модели

По исходникам ASR engine остаётся в `cachedEngine`, затем вызывается генерация итога. Значит, даже последовательные стадии могут удерживать ресурсы одновременно. Это не измерение утечки; это место для сравнения политики удержания/освобождения на малых Mac.

Предлагаемые эксперименты, сейчас не реализованные:

1. На малой памяти освобождать ASR перед LLM; сравнить с кешированием при серии встреч.
2. Один inference job одновременно. Тяжёлые итоги выполнять после записи, без конкуренции с захватом звука.
3. Не запускать reasoning на простом преобразовании источника, если отключение поддерживается и подтверждено runtime. У LFM3 это отдельно проверяемый риск.
4. Не загружать вторую генеративную модель только ради заголовка или пары тегов.
5. Подбирать контекст по реальному объёму и резерву на ответ, а не резервировать 128K/256K по максимуму карточки.
6. Сохранять полное исходное содержание, разбивать по репликам/темам, не делать повторное агрессивное сжатие уже сокращённых итогов.
7. После очереди выгружать модель по разумному idle timeout; не выгружать после каждого chunk, если это заставляет постоянно загружать веса заново.
8. Измерять cold start и warm processing отдельно. Скорость токенов и общая стоимость задания — разные показатели.

Квантизация Q4/Q5 снижает размеры весов, но не пропорционально весь footprint. Помимо весов остаются cache/state, buffers, runtime, ASR, приложение, macOS и пользовательские программы. GPU/ANE не означают нулевую нагрузку или гарантированную экономию энергии.

## 8. Минимальный честный сравнительный тест

Первый набор: текущая `gemma4:latest` с зафиксированным digest, Qwen3.5-4B Q4, LFM3-1.7B Q4, при необходимости Gemma 4 E2B. Выбирать одну модель по итогам теста, не устанавливать пользователю все четыре.

Корпус: 12 синтетических или явно разрешённых обезличенных разговоров — RU, EN и смешанные; короткие, 30–60 минут и длинные; рабочие и личные. Включить позднюю смену срока, отмену решения, однофамильцев, шутку вместо обещания и неоднозначное обращение. Для каждого заранее подготовить факты, решения, сроки, говорящих и неизвестные значения.

| Метрика | Как считать |
| --- | --- |
| Полнота | Доля эталонных значимых фактов, сохранённых с верным смыслом |
| Достоверность | Доля утверждений с опорой на источник; отдельно критические выдумки |
| Действия | Precision/recall действий, ответственных и сроков; явно учитывать `неизвестно` |
| Атрибуция | Ошибки назначения факта/имени другому человеку |
| Скорость | End-to-end на весь разговор; cold/warm отдельно; медиана и худший случай |
| Ресурсы | Пик общей памяти, memory pressure, swap, влияние на отзывчивость и запись |
| Энергия | Energy per finished meeting, если доступны разрешённые средства измерения |
| Стабильность | Незавершённые ответы, скрытое reasoning, retries, обрыв контекста |

Проводить минимум три повтора с одинаковыми настройками и требованиями к подробности. Не ускорять кандидата тем, что он пропустил половину источника. Критические выдуманные решения, диагнозы или подмена участника — блокер даже при хорошем среднем балле. Порог полноты определить на размеченном корпусе; произвольный ROUGE не заменяет проверку фактов.

Для backend-сравнения сначала фиксировать модель/quantization, затем менять GGUF/MLX. Для сравнения моделей фиксировать backend, контекст и формат результата насколько возможно. Чужие цифры H100/RTX5090/M5 нельзя подписывать как показатели M4 Pro или MacBook Air.

## Рекомендуемое решение после исследования

**Практичный следующий шаг:** небольшой сравнительный прогон Qwen3.5-4B и LFM3-1.7B против текущей Gemma. До измерений основной кандидат — Qwen; кандидат на минимальные ресурсы — LFM3. Нельзя пока честно сказать, кто из них «лучше справляется» именно с нашими подробными заметками.

**Архитектура продукта:** локальные файлы для хранения → точный индекс и при необходимости embeddings для поиска → одна компактная модель по требованию для связного текста. Decision-модель добавлять только при измеримом выигрыше на извлечении/тегах; специализированное дообучение — после появления корпуса. Диффузионные модели, большие MoE и новые движки оставить отдельными экспериментами, не обязательными зависимостями первой версии.
