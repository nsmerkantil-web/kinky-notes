# План реализации и передача следующим агентам

Дата: 2026-10-27. Основание: [исследование](RESEARCH.md). Все этапы ниже ещё предстоит выполнить. Исследование не является разрешением сейчас устанавливать приложение, запускать запись или загружать личные встречи в облако.

## 1. Рабочие решения

- Платформа первого релиза: macOS, Apple Silicon, целевой компьютер M4 Pro / 48 GB / macOS 26.6.2.
- Источники: Microsoft Teams desktop и **Google Chrome**, подтверждённый пользователем. Обязателен Google Meet и позднее фактическая сторонняя площадка пользователя.
- Языки: RU, EN, mixed RU/EN. Белорусский отложен.
- Локальные данные и локальная обработка по умолчанию, без обязательного аккаунта/сервера.
- Три режима запуска: вручную, предложение, автоматический. Auto — обязательная функция MVP, а не забытый backlog.
- Аудиозапись сохраняется и доступна для прослушивания; политика хранения настраивается.
- Разделение говорящих: источники сразу, финальные Speaker A/B/C до завершения MVP; реальные имена через интеграции позже.
- Рекомендуемый стек собственной реализации: SwiftUI/AppKit + Core Audio + SQLite + сменные локальные ML workers. Решение уточняется после проверки готовых открытых основ и аудиопрототипа.

Имена агентов следуют пользовательскому правилу: вариации имени Антон; для моделей выше уровня Luna — суффикс «с усами». Ниже указаны роли для будущей работы, а не уже запущенная команда. Модели и исполнители не назначены. Параллельный запуск возможен только при отдельном разрешении или применимых инструкциях.

## 2. Этапы и выходные артефакты

### P0 — ограниченная проверка возможности переиспользования

Ориентир: 1–2 инженерных дня. Проверить Meetily Community и Anarlog community на фиксированном revision. Для каждого: структура, license boundary, фактические локальные зависимости, сетевые обращения, два аудиоисточника, заменяемость моделей, папки/редактор, сложность сборки. Не переносить claims Pro/enterprise на открытый продукт.

Артефакт: `docs/decisions/0001-build-or-reuse.md` с таблицей «проверено / отсутствует / неизвестно», revision и командой воспроизведения. Решение: fork конкретной основы либо собственный небольшой проект. Timebox не расширять бесконечно из-за сборки чужой монорепы.

Gate: обоснован один основной путь. Если доказательств пригодности готовой основы нет, выбирать собственную реализацию, сохранив полезные ссылки.

### P1 — технический прототип записи и детектора

Ориентир: 3–5 дней. Минимальный `.app`, стабильный bundle ID, разрешения и меню Start/Stop. Запись mic + remote в разные файлы. Лог событий содержит типы/время/диагностику, но не содержание речи. Core Audio основной кандидат; ScreenCaptureKit сравнивать при конкретной проблеме, не строить второй движок ради абстракции.

Детектор пока работает в режиме наблюдения: отмечает кандидатов без автоматической записи. Проверить Teams, Chrome Meet, mic-test, диктовку, закрытие/открытие приложения, выход из звонка, звонок с выключенным микрофоном. Выяснить helper-process mapping и поведение mute.

Артефакты: prototype, `docs/validation/capture.md`, анонимизированный журнал, короткие тестовые файлы вне git, карта подтверждённых/неподтверждённых сценариев.

Gate: 60 минут контролируемого звонка, обе стороны слышны, воспроизведение не изменено, нет необъяснённых разрывов; тест route change и sleep показывает корректные ошибки/границы. Дрейф между дорожками целевой <100 ms за час. Каждый обнаруженный gap должен иметь запись в журнале. Это целевые критерии, а не уже полученные результаты.

### P2 — выбор локального ASR и суммаризации

Ориентир: 3–5 дней. Воспроизводимый набор: минимум 10 минут размеченной RU-речи, 10 EN, 10 mixed, плюс тишина, имена, числа, перебивания и низкое качество. Использовать разрешённые тестовые записи, не брать архив личных бесед по собственной инициативе.

Сравнить whisper.cpp large-v3-turbo и large-v3; WhisperKit добавить как сопоставимый вариант на Mac. Измерять весь pipeline двух дорожек, а не скорость одного файла. Локальные итоги — baseline класса 8B и один более крупный вариант при необходимости. Зафиксировать модели, quantization, runtime revision, память, температуру/thermal state, скорость, cold start.

Артефакты: `docs/validation/asr-benchmark.md`, `docs/decisions/0002-models.md`, manifest корпуса с эталонными текстами, схема evaluation.

Gate: выбран один ASR/runtime и одна summary-модель по данным. Цели качества из раздела 4 пройдены либо отклонения явно представлены пользователю; не объявлять mixed support только по списку языков модели. Не добавлять облачный fallback молча.

### P3 — устойчивая вертикальная alpha

Ориентир: 4–6 дней. Полный путь: ручной старт → chunk recording → live draft → финальный текст → итог → сохранённая встреча → открытие после перезапуска. Очередь jobs переживает crash; запись важнее inference; интерфейс показывает degraded state.

Хранилище версий заметок и сегментов, экспорт JSON/Markdown, восстановление незавершённой встречи. Запись в Application Support; модели отдельно. Если ASR/LLM падает, аудио и ручные заметки доступны.

Gate: несколько последовательных встреч без дублей/потерь; kill process и повторный старт восстанавливают завершённые chunks. Повторная обработка не дублирует текст и не стирает ручные исправления.

### P4 — автоматическое поведение и management

Ориентир: 4–6 дней. Реализовать все три режима, overrides по Teams/Chrome, Ignore, подавление повторов, auto-stop с grace period, ручное разделение встреч. Собственное небольшое окно предложения, индикатор записи, Pause/Stop доступны из menu bar. Соблюдать политику видимости/отключения уведомлений самого приложения.

Добавить папки, поиск, редактор, версии итогов, корзину, восстановление, окончательное удаление, audio playback с переходом по таймкоду, настройки хранения и базовые шаблоны. Заголовок по умолчанию из даты/источника; LLM-заголовок не затирает ручной.

Gate: сценарии таблицы ниже пройдены. «Предлагать» не сохраняет аудио до Start; «Автоматически» начинает новую разрешённую сессию без клика и не перезапускает ту, которую пользователь остановил.

### P5 — групповые голоса и качество результата

Ориентир: 3–5 дней, может потребовать больше из-за эха/overlap. Сравнить SpeakerKit OSS и pyannote baseline на небольшом размеченном наборе. Выбрать один production-вариант. Speaker IDs стабильны внутри встречи, rename работает по всей встрече, неизвестные/перекрывающиеся участки отображаются честно.

При встроенных динамиках проверить дубли и ошибки attribution. Для каждой заметки — проверяемые ссылки на исходные сегменты; длинный двухчасовой транскрипт обрабатывается полностью. Проверить конфликт пользовательской правки и фоновой перегенерации.

Gate: диаризация проходит согласованную метрику, заметки не содержат выдуманных решений/ответственных на контрольном наборе. Если этап не пройден, продукт остаётся alpha с ограничением, а не «полностью повторяет Granola».

### P6 — личная beta и упаковка

Ориентир: 4–7 дней инженерной работы плюс примерно неделя реальных разрешённых тестов. Стабильная установка, permissions UX, optional launch at login, обновление без потери базы, backup/restore, отключение сети, disk-full и worker-crash тесты. Проверить actual Teams/Chrome versions, реальные наушники и стороннюю площадку пользователя.

Gate: пользователь может несколько рабочих дней пользоваться приложением без восстановления вручную; ни одна ошибка не выглядит как успешно записанная встреча. Есть install/run/recovery инструкция и список известных ограничений.

Суммарный ориентир: 22–36 инженерных дней, примерно 4–8 календарных недель при последовательной работе и доступных тестовых звонках. Это диапазон планирования с низкой уверенностью, не обещание сроков AI-агентов. Успешный reuse может сократить UI-часть; эхо, диаризация и неподтверждённый сайт могут увеличить срок. Срок пересчитать после P1/P2.

## 3. Контракты между модулями

До разделения задач закрепить короткие versioned контракты. Не отдавать каждому исполнителю право придумать несовместимый формат.

| Модуль | Вход → выход | Инвариант |
|---|---|---|
| CallDetector | OS events → Candidate/Ended evidence | Сам не начинает запись |
| CapturePolicy | evidence + prefs + session state → action | Ignore/Stop не переигрываются тем же событием |
| AudioCapture | target/device → PCM chunks + metadata | Два источника, монотонное время, gaps явны |
| RecordingStore | chunks → durable manifest | Завершённые chunks восстанавливаются |
| TranscriptionEngine | audio span + options → draft/final segments | Stable IDs/revisions, no translation by default |
| DiarizationEngine | remote audio → speaker intervals | Unknown допустим, имена не угадываются |
| NotesEngine | transcript revision + manual revision + template → summary | Evidence IDs; исходники не меняются |
| MeetingRepository | mutations/queries → persisted records | Транзакции, версии, tombstones |
| JobScheduler | versioned inputs → retryable jobs | Idempotency; delete отменяет jobs |

Каждый chunk: session ID, track ID, sequence, monotonic start, sample rate, channels, frame count, checksum, gap metadata. Wall-clock дата хранится отдельно. Pause, device change и sleep имеют явные события на общей шкале.

Job key включает meeting ID, input revision, model revision и options hash. Если встреча удалена или вход изменился, устаревший job не должен воскресить удалённые данные или перезаписать новый результат. Export schema version независима от внутренней схемы SQLite.

## 4. Матрица приёмки

Пороги ниже — начальные цели разработки. Их можно изменить с объяснением результатов, но нельзя задним числом выдать неуспех за прохождение.

| Область | Проверка | Целевой результат |
|---|---|---|
| Детектор | 20 стартов/завершений: Teams и Chrome Meet | ≥95% обнаруженных в этом наборе; p95 предложения ≤3 s от наблюдаемого OS-сигнала; это не гарантия любых сайтов |
| Негативные примеры | 20 сценариев: YouTube, диктовка, mic-test, просто открытый Teams | Для настроенных политик ≤1 ложного предложения; автоошибки отдельно отчётить |
| Начало записи | Auto warm start | p95 ≤2 s после решения policy; время до сигнала отдельно |
| Ручное управление | Start/Ignore/Pause/Stop/New meeting | Нет повторного запуска в подавленной сессии; pause не пишет скрытое аудио |
| Две дорожки | 60 минут, затем 120 минут soak | Обе стороны доступны, bounded RAM, нет необъяснённых дыр |
| Устройства | Built-in, используемые AirPods/USB, route change | Нет crash; смена/разрыв отражены в timeline |
| Mute | Teams mute; локальная Pause; удалённая тишина | Поведение прозрачно; микрофон приложения управляется явно |
| Браузер | Meet + другая звучащая вкладка; reload; helper restart | Известно, что попадает в запись; scope не расширяется молча |
| Границы | Back-to-back, два приложения одновременно, sleep/wake | Нет скрытых merge; в MVP один активный recorder, второй кандидат не создаёт двойную запись |
| ASR | Размеченные RU/EN/mixed с одинаковой нормализацией | Начальная цель WER ≤15% clean RU/EN; ≤25% mixed; числа/имена отдельной проверкой |
| Live ASR | Teams video + Chrome + двухдорожечный pipeline | Очередь не растёт постоянно; p95 появления текста ≤10 s после конца фразы; RTF pipeline <1 |
| Тишина | 10 минут без речи | Нет выдуманных фраз; не завершает активную встречу автоматически |
| Говорящие | 1:1 и 3–4 участника, размеченные интервалы | DER целевой ≤20% на remote; фиксировать collar/overlap policy и результаты отдельно |
| Summary | 10 контролируемых встреч, включая длинную | Все проверяемые утверждения имеют корректные источники; 0 выдуманных решений/владельцев; ≥90% контрольных ключевых фактов |
| Performance | Повторяемый сценарий под нагрузкой | Нет постоянного swap/ухудшения звонка; peak RAM и latency записаны, а не угаданы |
| Crash | Принудительно остановить app/worker | Завершённые chunks восстановлены, потеря не больше последнего незавершённого фрагмента; целевой fragment ≤5 s |
| Диск/доступ | Заполнить тестовый том, отозвать разрешение | Явная ошибка и доступ к уже сохранённому, не статус «успешно» |
| Offline | После загрузки моделей запретить сеть | Capture → ASR → summary → search работают; нет сетевого fallback |
| Редактирование | Правка во время final ASR/summary | Ни одна ручная правка не теряется |
| Удаление | Удалить встречу во время job; очистить корзину | Удалены связанные аудио/текст/индекс/промежуточные данные; job не воскрешает запись |
| Backup | Экспорт → чистая тестовая база | Заметки, папки, таймкоды и ссылки на аудио восстановлены |

Сохранять отдельно результаты для каждого браузера/площадки/устройства. Не переносить успешный тест Meet на неизвестную психологическую платформу. Наушники и встроенные динамики — разные строки результата.

## 5. Будущие исполнители

Имена ниже условные для моделей уровня Terra/Sol; для Luna убрать «с усами».

| Роль | Имя | Ответственность и результат |
|---|---|---|
| Ведущий | Антон с усами | P0, ADR, контракты, интеграция, scope и итоговый статус |
| Аудио | Антонио с усами | P1, capture/detection, device matrix и восстановление |
| Речь | Антонина с усами | P2/P5, ASR/диаризация, корпус, метрики и model manifest |
| Данные и UI | Энтони с усами | P3/P4, хранение, редактор, папки, управление записью |
| Проверка | Антонитика с усами | P6, независимые end-to-end сценарии и отчёт ограничений |

Сначала ведущий фиксирует P0 и контракты; аудиопрототип P1 — на критическом пути. P2 можно выполнять на тестовых файлах до UI. P3 интегрирует результаты; P4/P5 зависят от устойчивого хранилища. Не раздавать разным агентам одни и те же файлы capture lifecycle или миграций без одного владельца.

Каждая передача содержит: конкретный objective, допустимые каталоги, контракт, зависимые решения, критерии приёмки, команды проверки, запрещённые предположения, формат отчёта. Отчёт всегда разделяет implemented / tested / not tested / known failures.

## 7. Следующие возможности после MVP

1. Имена Teams через Accessibility и Google Meet через Accessibility/extension; независимые адаптеры, отсутствие сигнала не ломает запись.
2. Календарные события как вспомогательный контекст; корпоративные OAuth/admin restrictions рассмотреть отдельно.
3. Chat по встрече, затем папке/архиву с источниками; удаления обновляют поисковый индекс.
4. Импорт доступного архива Granola и аудиофайлов, дедупликация по внешнему ID.
5. Windows 11 adapter/UI, переносимость форматов и одинаковые contract tests.
6. Белорусский benchmark и политика mixed RU/BE/EN после базовых языков.

Открытые уточнения перед beta: фактическая площадка психолога; устройства ввода/вывода; желаемый срок хранения аудио; нужно ли отдельное шифрование сверх FileVault; допускаются ли когда-либо облачные модели. Эти вопросы не блокируют P0/P1.
